# sentinel-agent

The server half of **Sentinel**, an iPhone app for watching your own Linux servers over SSH: their
health, services, containers, hardware, websites and game servers.

The agent is one Python file with no dependencies. It is not a daemon: there is no open port, no
web service and nothing listening. The app opens an SSH session to the server and runs the agent
once per refresh, through a key that can run nothing else.

```
  iPhone ── SSH (Ed25519, host key pinned) ──► sshd
                                                 │  forced command
                                                 ▼
                                      /usr/local/bin/sentinel-agent
                         ┌───────────────┬──────┴───────┬──────────────────┐
                    /proc, /sys     systemd, docker   hwmon, ipmitool,   websites, ports,
                                                      smartctl,          game servers
                                                      nvidia-smi
```

## Install

The app shows the exact command, with its own key and the installer's checksum filled in. Run it
on the server (or from a computer, wrapped in `ssh -t you@server '…'`):

```bash
f=$(mktemp) && curl -fsSL https://n3d-store.com/sentinel/2.0.0/install.sh -o "$f" && echo "<sha256>  $f" | sha256sum -c --quiet - && sudo bash "$f" --key <key>
```

Or download it yourself, read it, and run it:

```bash
sudo bash install.sh --key "ssh-ed25519 AAAA… sentinel-iphone"
```

What it does:

1. Checks the server: systemd, Python 3.8+, bash 4, sudo with `/etc/sudoers.d`, OpenSSH.
2. Puts the agent at `/usr/local/bin/sentinel-agent`. The installer carries it inside itself and
   checks its SHA-256 first.
3. Creates the account `sentinel`. It has no password, a root-owned `~/.ssh`, and nothing to do
   but run the agent. `--user` picks an existing account instead.
4. Looks at what the server runs and writes `/etc/sentinel-agent.conf`:
   - the running services, minus the operating system's own machinery;
   - the running containers, and those with a restart policy;
   - whichever hardware sources exist.
5. Writes `/etc/sudoers.d/sentinel-agent` (below), after `visudo` has checked it.
6. Adds the phone's key as a forced command: `restrict,command="/usr/local/bin/sentinel-agent"`.
   That key cannot open a shell, forward a port or run anything but the agent.
7. Runs the agent once as that account, the way the phone will, and prints the server's host key
   fingerprint for you to compare with the app.

Re-running is safe: the agent and the rules are replaced, the config is merged (never clobbered),
and a key that is already there is not added twice.

| Option | |
|---|---|
| `--key <key>` | authorise a phone's key |
| `--user <name>` | log in as an existing account instead of `sentinel` |
| `--allow-control` / `--read-only` | allow or forbid start/stop/restart (read-only by default) |
| `--detect` | look for new services, containers and hardware (nothing is ever removed) |
| `--check <url \| host:port \| minecraft:host:port \| a2s:host:port>` | watch a website, port or game server |
| `--remove-key <SHA256:… \| comment>` | revoke one phone (a lost one, say) |
| `--uninstall` | remove the agent, its rules, its keys, its config and its account |

## What it may do as root

The account has no blanket sudo and is in no privileged group. It is not even in `docker`, which
is root in all but name. Its whole grant is the drop-in the installer writes, generated by
`sentinel-agent --sudoers` from the exact command lines the agent runs. Every entry is one complete
command, with no wildcards. sudo matches the whole line, so nothing can be appended to any of them.

**Always** (read-only):

| Command | Why |
|---|---|
| `docker ps -a --no-trunc --format {{json .}}` | the container list |
| `docker stats --no-stream --no-trunc --format {{json .}}` | container CPU and memory |
| `docker logs --tail 500 --timestamps <container>` | logs, one rule per watched container |
| `journalctl -u <unit> -n 500 --no-pager -o short-iso` | logs, one rule per watched service |
| `ipmitool sdr elist`, `ipmitool sel elist last 200` | the BMC's sensors and event log, if there is a BMC |
| `smartctl -j -n standby -H -A -i [-d type] <dev>` | drive health, one rule per drive |

Logs are always read at 500 lines and trimmed by the agent, so that each rule can name one exact
count. These reads are not written to the auth log (where sudo is new enough), because the app
polls every few seconds.

**With `--allow-control`**, for what the config lists under `control` and the checks that have
controls:

| Command | |
|---|---|
| `systemctl start\|stop\|restart <unit>` | a controllable service |
| `docker start\|stop\|restart <container>` | a controllable container |
| `systemctl enable --now` / `disable --now <unit>` | a game server's start and stop, so a stopped one stays stopped |
| the exact commands a check names | e.g. a game server's own save-then-stop script |

A **lifeline** can only ever be restarted, never stopped, whatever the config says. Stopping one
can cut off every way back in, including the one the phone is using. The lifelines are ssh/sshd,
tailscaled, NetworkManager, systemd-networkd, systemd-resolved, networking, wpa_supplicant,
docker, containerd, cloudflared, wg-quick@…, openvpn… and zerotier-one.

Losing the phone therefore costs a read-only view of the server, plus the controls you allowed. Run
`--remove-key` to revoke it.

## The config

`/etc/sentinel-agent.conf` is JSON, and it is the security boundary: the agent shows and touches
only what it names. Edit it, then run the installer again, so that the sudo rules follow.

```json
{
  "allow_control": true,
  "units": ["nginx.service", "postgresql@16-main.service", "ssh.service"],
  "containers": ["app", "redis"],
  "control": {"units": ["nginx.service"], "containers": ["app"]},
  "checks": [
    {"kind": "http", "url": "https://example.com", "contains": "Welcome"},
    {"kind": "tcp", "host": "127.0.0.1", "port": 5432, "label": "Postgres"},
    {"kind": "minecraft", "key": "mc", "host": "127.0.0.1", "port": 25565,
     "control": {"unit": "minecraft.service", "hints": {"start": "about a minute until it can be joined"}}},
    {"kind": "a2s", "host": "127.0.0.1", "port": 28016}
  ],
  "hardware": {"sensors": true, "ipmi": false, "smart": [{"dev": "/dev/sda", "type": "sat"}], "gpu": false},
  "thresholds": {"Inlet": {"warn": 42, "crit": 47}}
}
```

- **`checks`** are probed from the server, every `checks_interval_s` (60 s) at most. The kinds:
  - `http` — `url`, optional `contains`, `expect` (a list of status codes) and `insecure` (skip
    certificate checks);
  - `tcp` — `host`, `port`;
  - `minecraft` — the Java Edition server list ping;
  - `a2s` — Valve's server query, for Rust, CS, Valheim, ARK and others;
  - `dashboard` — a status dashboard's JSON, whose games and sites become checks.
- **A check's `control`** is either `{"unit": "x.service"}` or
  `{"commands": {"start": [...], "stop": [...], "sleep": [...], "restart": [...]}}`. A command is an
  absolute path to a root-owned file, plus plain words. `container` names the container the check
  runs in: that container is then never started or stopped bare. `hints` are shown while a verb
  runs.
- **`thresholds`** override a sensor's warn/crit by its label. The kernel's sensors bring their
  own, and a BMC reports its own status, so most servers need none.
- **`paths`** (written by the installer) are the absolute paths sudo matches.

## Uninstall

```bash
sudo bash install.sh --uninstall
```

This removes the agent, its config, its sudo rules, every key line that forces it, and the
`sentinel` account it created. An account you chose with `--user` is left alone, apart from those
key lines.
